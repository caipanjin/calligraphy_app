# 书法临摹助手

把任意字帖（手机拍照、公众号图片）切分成单字，逐字放大临摹的移动应用。

**纯本地运行，无服务器、无账号、无模型依赖。** 所有数据（字帖、切分结果、练习记录）都存在设备的 IndexedDB 里。

---

## 功能

### 字帖库

- **一本字帖 = 多张页图**：一次选中多张照片就合成一本可翻页的字帖，之后还能继续加页
- 最多 **20 本 / 每本 30 页**，一次最多选 20 张；支持重命名、删单页、删整本、清空全部
- 卡片显示封面缩略图、名称、页数、体积、**练习进度条**（各页已练字数之和 / 总字数）
- 打开字帖后底部列出**本字帖**所有页的缩略图（进入可视区才按需读，240px 小图），
  左右滑动翻页；不同字帖之间的页互不关联
- **关闭字帖（返回字帖库）会释放该字帖在内存里的所有内容**：当前页原图、选中单字、
  切分面板与缩略图缓存全部清空，磁盘数据与「上次临摹到哪一页」保留，重开自动恢复
- 删除整本字帖不清掉按图片内容哈希存的切分/练习记录 —— 同一张图若在别的字帖里，
  两边的进度共享；孤儿记录由「清空全部字帖」统一回收

### 自动切字（投影法）

纯前端的字符切分，**毫秒级、无需模型**：

- **默认竖排**，从右往左、从上往下阅读
- 支持**有格字帖**（自动检测格线）与**无格字帖**（投影 + 字距拟合）
- 字框按每个字**真实墨迹范围**取宽取高，避免笔画探出被裁
- 打开字帖即显示切分结果，无需手动触发

> 为什么不 OCR：实测通用 OCR 引擎（Tesseract 5/8、PaddleOCR 0/8）对毛笔字全部识别失败，
> 改以投影切分解决「字在哪」的问题，效果远好于识别。

### 手动编辑切分框

自动切分不可能 100% 准确，编辑态提供逐字修正：

| 操作 | 用途 |
|---|---|
| 删除 | 去掉多余的框（如底部残块）|
| 合并 | 一个字被切成两框 |
| 拆分 | 一个框装了多个字 |
| **加框** | 补切分漏掉的字 —— 支持**单击生成默认大小的框**（尺寸参考同列字）或**拖拽画框** |
| **拖动 / 拉边角** | 直接移动框、单独调整四条边，每个字的高度独立 |
| **本列切线** | 选中一列任意框后开启；拖动公共边界切线，上下两框同步、不重叠不留缝 |
| **找候选线** | 只按**本列**行投影低谷给出「可能」的字间切线，点编号选取后重切本列 |
| 撤销 | 逐步回退连续调整（最多 20 步）|
| 还原 | 回到自动切分结果 |

> 设计边界：无格书法（尤其行书）各列字数、字距、字高都可能不同，同位字未必对齐，
> 字内笔画间隙甚至比字间还宽（实测某字内部 18px，另一列真字间只有 9~12px）。
> 因此编辑能力**一律只作用于本列、由人判断**，不做跨列对齐、不按字数等距重排，
> 候选线只作建议。实测一张 4 列行书字帖同位字字心极差最大 157px（17.8% 图高）、
> 字间空白 -4~43px（含框重叠与连写穿插）。
> 编辑结果写入 `:manual` 缓存并永久豁免算法版本，不触碰自动切分算法与 golden 快照。

### 单字临摹

- 点击任意字进入单字视图，**拖动平移、双指缩放**，桌面端可用 `+/-` 缩放、`PageUp/PageDown` 换字、`Esc` 返回
- 底部缩略图条显示相邻字，**当前字与主视图实时同步**（缩放/位移都一致）
- minimap 全景导航，红框标出当前位置
- 「上一字 / 下一字」按真实字框跳转，不会错位

### 练习进度

- 进入单字**停留 ≥ 3 秒**自动记一次练习（快速浏览不误记）
- 字帖卡片显示进度条，设置页显示**今日 / 近 7 天 / 累计**统计
- 打开字帖自动**续练**到上次练到的字（可关闭）
- 调整框或重新切分时会提示「会重置练习记录」，需确认

### 从公众号导入

两种方式：

1. **粘贴链接** —— 在 App 内粘贴公众号文章链接，自动抓取正文图片
2. **剪贴板提示** —— 复制公众号链接或图片后打开 App，顶部自动提示导入

抓取与过滤逻辑：

- **正文图片提取**：按微信页面的明确标记排除封面（`og:image` / `msg_cdn_url`）、
  作者头像（`jump_author_avatar`）、二维码（`js_qrcode_img`）等干扰图
- **尺寸过滤**：宽高 ≥ 300px、比例 0.33~1.5、正方形且 <1000px 视为头像/二维码
- **视觉去重**：公众号会把同一幅字帖导出成多个尺寸/裁切，用 **16×16 灰度指纹 + 归一化距离**
  识别为同一张，保留分辨率最高的版本
- 抓取结果缓存 10 分钟，避免触发微信风控

> 已知限制：微信对抓取有频率限制，短时间内多次请求会返回「精简页」。
> App 会识别并提示等待，不会误报「没有图片」。

### 其他

- 浅色 / 深色主题
- 移动端优先，适配 iPhone 安全区
- iOS / Android 原生打包（Capacitor 6）

## 技术实现

### 切分算法（`src/utils/segment.js`）

```
灰度化 → 装裱边框检测（命中则零化边框、只在纸区内算阈值）→ Otsu 二值化 → 墨迹掩码
  → 列投影（竖排）→ findBands 找列
  → 每列内行投影 → 找字带 → 过高字带按空白引导切分（切点避开笔画）
  → 按字距 pitch 拆分粘连列（单列大字、笔画级伪字距跳过；贴边细带剔除、窄间隙合并）
  → 每字四边按真实墨迹范围扩展（受相邻字空隙约束）
  → 异常块过滤（单列大字特写的宽度上限单独放宽到整幅）
```

关键参数：

- **装裱边框检测**（`detectContentBorder`，v11）：白纸黑字字帖常被深色装裱边/黑底包围，
  暗色占比可能 >60%，会骗过反色判据（误当成黑底白字拓片），边框本身也被当成墨迹把图切碎。
  检测浅色纸区包围盒，命中时把边框零化、只在纸区内重算 Otsu 与反色。四重守卫防误裁：
  内容区面积 <92% 全图、左右各内缩 ≥4%（排除 UI 状态栏这类单侧暗条）、区内浅色占比 ≥50%
  （排除拓片上稀疏的白色笔画）、区外暗色占比 ≥60%。实测 1968×3840 装裱对联暗色 66% 误反色、
  旧切 16 框穿字，修复后纸区内阈值由 123 变 145、切出 23 框（右联 12 字逐字成框）；
  13 套既有夹具源图全部不命中、掩码逐字节不变
- 相对阈值：90 分位 × `INK_RATIO=0.15`，配 3 点平滑，抗噪
- 字距自相关的搜索上限默认 **40% 图宽**；仅当列投影呈「双联形态」（恰好两条窄列带、
  宽度接近、列心距在 0.4W~0.55W 之间）时放宽到 **55%**，否则真实列周期会被排除、
  锁到笔画级短周期并把两联误拆成 6 列。判据刻意收紧：导入面板缩略图网格等重复图案
  在 0.47W 附近有更强伪周期，全局放宽会把多列并成一列
- **贴边细带不算一列**（`isNegligibleEdgeBand`）：拓片/照片的浅色纸边会在列投影
  边缘留下一条极窄带。宽度 < 5% 图宽、且起点或终点贴到图边缘 0.5% 内时忽略它，
  单列大字判据先剔除这类细带再数实质列带，命中时也从最终列带里删掉。
  实测 541×1082 黑底拓片右侧 `[533,541]` 仅 8px、墨迹只在上半幅；旧判据要求
  「恰好 1 条列带」故不命中，主带被 43px 笔画级字距拆成 11 列 / 124 个小框
- **窄间隙列带并回一列**（`mergeNarrowGaps`）：大字内部（左右结构、长竖之间）会有
  贯穿全高的投影低谷，它并非列间空白，却会跌破 `findBands` 相对阈值：
  527×1090 黑底「作我」拓片 x229~237 仅 8px（该区域按 y 分桶仍有数百墨迹像素），
  而 minGap 只有 4px，一列被劈成 `[59,229]` / `[237,474]` 两列、切成 7 框。
  只合并间隙 < **2% 图宽** 的相邻带（真实两列空隙远大于此），返回新数组不改原带；
  并且只在判据确实发生过合并时，才跳过下面「带宽 ≥ pitch×2.5」的保守条件
  —— 这类图 pitch 会锁到约半个带宽（实测 211 vs 合并带宽 415），未合并的图逻辑完全不变
- **单列大字特写跳过字距拆列**（`isSingleWideColumn`）：剔除贴边细带、合并窄间隙后
  只剩一条铺满大半幅宽的列带、且带宽与典型字高相当时，列投影里的周期来自笔画而非
  列间距，把字距视为 0。实测 531×1080 黑底「我則」拓片：带宽 420px、字高 462px、
  pitch 却锁到 42px，不跳过就会被拆成 10 列 / 132 个 42×45 小框。判据只看几何，
  不用自相关得分阈值 —— 整张界面截图 0.213、大字特写 0.171、带纸边的拓片 0.468、
  带投影低谷的拓片 0.300，得分根本无法区分；而「带宽/字高」分别是 2.93 与 0.91，
  区分明确
- **多列版式的笔画级伪字距**（`isStrokeLevelPitch`）：`isSingleWideColumn` 只认
  「恰好一条实质列带」，覆盖不到正文列 + 印章列这类多列版式。实测 523×1068 黑底
  「翁同龢書」拓片有 `[79,210]`（印章列，宽 131）与 `[327,463]`（正文列，宽 136）两条带，
  `needsWidePitchSearch` 误判成双联放宽搜索上限，`estimatePitch` 却锁到 pitch=42
  （score 0.397，只有列宽 1/3 的笔画宽），把两条带各拆 3 列、切成 6 列 / 53 个小框。
  判据只看几何：列间距不可能比任何一条真实列带还窄 —— 先剔除宽度 < **5% 图宽** 的
  细伪带，要求剩余 ≥ 2 条实质列带且 `pitch < 0.6 × 最窄实质列带宽` 时把字距视为 0。
  **只有一条宽列带时必须放行**：`full-screenshot`（`[0,739]` / pitch 59）与
  `dense-grid`（粘连多列 / pitch 120）都真的需要按字距拆列，全局置 0 会破坏这两套夹具
- **单列大字的宽度上限单独放宽**（`maxBoxWidthRatio`）：异常块过滤默认丢弃宽/高
  > **85% 图幅**的框（通常是「整页被当成一个字」）。但单列大字特写的列带本身就是
  字宽：550×1082 黑底「凡厥」拓片列带宽 469px、量测后框宽 473px，而 `0.85W` 只有
  467.5px，两个正确框被全部删掉、返回「切分失败 / 0 框」（前三张大字拓片列带宽占比
  都 < 0.79，本图 0.8527 只越线 5.5px）。命中 `isSingleWideColumn` 时只把**宽度**
  上限放宽到 **100%**（v10 由 95% 再放宽：水平扩展改用列间空隙后，单列大字的笔画
  可合法伸到近整幅宽，「吝驕」次字框宽 541px = 整幅，95% 会误删成 1 框），
  高度仍保持 0.85H，整页单字的高框依旧被挡住
- **高字带按空白引导切分**（`blankGuidedCuts`）：行草里单字常明显高于列宽，旧的
  `splitTallGlyphs` 按列宽机械二等分/三等分，切分线直接穿过笔画。实测 415×1600 的
  4 列行草条幅有 6 条带被这样拆过，5 组单字各被切成两框（框垂直重叠 5~6px、
  交界处墨迹连续），真正的字间空白却在几十像素之外。现在等分只决定「切几刀」，
  每个切点单独校验：**本来就足够空**（7 行平均墨迹 ≤15%）就保留；**穿过笔画**
  就吸附到附近最长的连续空白段（行投影 ≤ 列宽 5%、至少 2 行、中点距带两端
  ≥0.45×列宽、搜索半径 0.3×等分步长）；**找不到空白**就撤销这一刀，整条带留作一个字。
  三等分带里只撤销/吸附其中一刀，正好得到「独立字 + 一个高字」。
  护栏必须同时满足：**等分份数 ≤3、带高 ≤3.2×列宽、带内墨迹 ≤35%**，
  其余情况一律走原来的等分 —— 不加护栏会把红底对联的 5 个字并成 746px 巨框，
  整张界面截图的退化检测也会少切框。该图 60 → 56 框，本来正确的相邻两框不动
- **超长字带按本列真实字距重切**（`rebandLongGlyphBand`，v12）：字距极密时（红底对联
  左联下半，真实字间空白只有 3 / 10 / 6 行，小于 `gapRow = 0.008H = 13px`），
  `findBands` 会把 5 个字并成 818px 的单一超长带；`blankGuidedCuts` 的三道护栏
  （五等分 >3 份、带高 3.86×列宽 >3.2、墨迹密度 0.518 >35%）全部不命中，
  只能按列宽机械五等分，切点落在 y≈1229/1426/1624、实际空白却在
  y≈1101/1364/1573，刀刀穿字。`parts ≥ 4` 且带高 ≥4×列宽时，先取本列行投影
  以 `minGap = 0.02×列宽`、`minSize = 0.35×列宽` 重跑 `findBands`；两道护栏兜底：
  **子带数 ∈ [max(3, parts−1), parts+1]、每条带高 ∈ [0.8, 1.6]×列宽**，
  任一不满足就完全回退原等分。刻意不全局下调 `minGap`（会让 `full-screenshot`
  从 165 框塌到 131 框）。该图左联 8 → 7 框、总 15 → 14 框，右联 7 框不动，
  其余 21 个 golden case 逐框零变化
- **水平扩展左右独立、按列间空隙限额**（v10）：书法字本身有大小差异，字框宽度
  不必一致、允许相邻框重叠。左右各自的上限取「到相邻列带边界的距离」（列间空隙）
  与「列宽 60%」的较小者，允许伸满列间空隙但不跨进邻列；单列无邻居时按列宽比例。
  旧版用「到最近墨迹的距离 ×45%」且左右共用最小值，本字笔画穿过列边界时最近墨迹
  就是笔画自己，限额被锁死 2px，裁掉长捺/撇尖（实测「吝」字真实墨迹 x=[0,540]，
  框却只到 [67,497]）。改用列带边界距离后，4 张大字拓片的框外墨迹基本清零
- 上下扩展分别用 `gapUp` / `gapDown`，避免末字被上方空隙限制

### 数据存储（IndexedDB，版本 5）

| Store | 键 | 内容 |
|---|---|---|
| `albums` | `album_x` | 字帖元数据：标题、时间戳、封面小图、各页 `{id, hash, size, addedAt}`；**不含原图** |
| `pages` | `page_x` | 单页完整 base64（`{id, albumId, dataUrl}`），只在打开该页时单条读取 |
| `thumbs` | `page_x` | 240px 缩略图，分页条进入可视区才按需读取 |
| `meta` | `current` | 续练指针 `{albumId, pageId}`，关闭字帖后仍保留 |
| `segmentations` | `{hash}:{layout}:{grid\|free}[:manual]` | 切分框、版面、单字调整、算法版本 |
| `segmentationSettings` | 图片哈希 | 版面模式、是否带格子线 |
| `practiceRecords` | `{hash}:{字索引}` | 练习次数、时间 |
| `practiceDaily` | `YYYY-MM-DD` | 每日练习汇总 |

**内存纪律**：字帖库只读 `albums` 元数据，绝不把 `pages` 的完整 base64 放进 React state；
切分 / 练习记录仍按「图片内容哈希」寻址，与字帖 id 无关，所以两本字帖放同一张图会共享进度。
缩略图在导入时生成并落盘（`buildThumbnail` 会挡掉「生成失败却回退成原图」的情况），
模块级缩略图缓存也改用图片哈希作 key，不再强引用整串 base64。
`buildInkMask` 的格线掩码（faint）只在有格模式计算：它的逐像素 7×7 邻域采样 + 排序
是掩码构建里最贵的一段（实测 415×1600 约 800ms、1600×1200 约 1.6s），免费布局与
候选切线只需要 ink，传 `withFaint: false` 整段跳过，切分输出不变。

**v4 → v5 是清空重建**：升级时删除旧 `images` store 并清空遗留的切分/练习缓存，
App 会提示重新导入，旧字帖与旧练习记录不迁移。全新安装只建表、不清理。

**`boxes` 是切分框的唯一数据源**：单字页的缩放/位移调整会直接写回切分框
（并打 `adjusted` 标记，后续进入不再额外加 padding）。

### 切分缓存的算法版本

每条切分缓存都带 `algorithmVersion`。打开字帖时只复用与当前版本一致的**自动**结果，
旧算法留下的记录会静默重算并**同键覆盖**（不产生孤儿键，也无需手动点「重新切分」）；
**手动调整过的框**（键以 `:manual` 结尾）是用户亲手确认的最终结果，不受版本影响，永久保留。

> 改动 `src/utils/segment.js` 里任何会改变「同一张图切出哪些框」的逻辑后，
> 必须把 `segmentCache.js` 的 `SEGMENT_ALGORITHM_VERSION` **+1**，
> 否则用户装了新版仍会命中旧缓存、看不到新结果。
> 改完跑 `npm test`：golden 夹具会把输出变化精确到「哪张图、第几框」，按需 `--update` 更新快照。

- **原生**：`CapacitorHttp` 走原生层，不受 CORS 限制
- **开发环境**：vite 自定义中间件（node 原生 https）

微信的请求头规律（实测，反直觉但稳定）：

| 请求头 | 结果 |
|---|---|
| 仅 UA | 200，含正文 |
| UA + Accept + Accept-Language | 302 跳验证码页 |
| 微信 UA | 302 跳验证码页 |

所以中间件**只发 UA**，且不透传浏览器的 Cookie / Referer / Sec-Fetch-*。

### 调试桥接（dev-only）：命令行直接读取当前打开的字帖

手工测试发现切分异常时**不必截图、不必导出发图**：只要 dev server 在跑并停在目标字帖页，
页面会自动把「当前原图 + 切分结果」写到本机临时目录，命令行 / AI 侧直接读文件即可复现与定位。

```bash
npm run dev                          # 默认 5173，启动时也会打印采集目录
DEBUG_DIR=$(python3 -c 'import tempfile,os; print(os.path.join(tempfile.gettempdir(),"calligraphy-debug"))')
ls -l "$DEBUG_DIR"                  # current.<ext> / current.json / state.json
# 扩展名随图片变化，从 current.json 的 file 字段取准确文件名
IMG=$(DEBUG_DIR="$DEBUG_DIR" python3 -c 'import json,os; d=os.environ["DEBUG_DIR"]; print(os.path.join(d, json.load(open(os.path.join(d,"current.json")))["file"]))')
node scripts/diagnose-segment.mjs "$IMG" --out /tmp/diag.png
```

| 落盘文件 | 内容 |
|---|---|
| `current.<ext>` | 当前页原图，扩展名由 MIME 决定；换页覆盖，旧扩展名自动清理 |
| `current.json` | 最近一次「带原图」的捕获：`updatedAt` / `source` / `pageId` / `file` / `mime` / `bytes` / `stores` |
| `state.json` | 每次上报都刷新的状态快照；`stores` 含 `segmentations`、`segmentationSettings`、`meta`、`albums`，另有 `storeNames` 表示库健康度：`null` = 库尚不存在（App 会自建，正常）、`[]` = 库存在却零表（坏库）、正常应含 `albums` / `pages` / `thumbs` / … |

采集策略：原图优先取 DOM 的 `img.stage-image`；单字模式 / 切分面板下没有它时，
走 `meta.current → pages` 读原图（`source: indexeddb:pages`），**绝不退化到 240px 缩略图**。
停在字帖库没打开字帖时抓到的是「上次练到的那一页」，看 `source` / `pageId` 即可分辨
（`stage-image` / `indexeddb:pages` / `none`）。MutationObserver + 3s 轮询驱动，
换页发全量包（含 dataUrl），仅切分框或版面设置变化发轻量包、不重传大图，
POST 到 dev server 的 `/__debug/report`（请求体上限 24MB）。

**命令行侧怎么用**
- `scripts/diagnose-segment.mjs`：Pillow 解码 + mock `Image` / `canvas`，直接跑生产
  `segmentCharacters`；打印逐层中间量（阈值、边框命中、墨迹占比、列带、pitch 等）与每框原图坐标，
  产出带编号红框叠加图、`*.ink.bin` 位压缩掩码、`*.json` 框坐标。需要 Pillow；
  `numpy` 只用于重新生成夹具，诊断不需要。
- `current.json` / `state.json` 里的 `stores.segmentations` 是**页面上正在显示的框**。
  用 `hashImageData` 重建当前图 dataUrl（注意带 `data:` 前缀）即可命中缓存键，
  与离线复现结果逐框对照，立刻区分「算法算错」还是「缓存 / 手动编辑造成的差异」。
- `scripts/verify-couplet-candidate.mjs`：候选算法 A/B 验证范式 —— 把 `segment.js` 读成文本、
  在内存里注入候选函数写到 `/tmp` 后动态 import，对同一批掩码跑 `segmentFromMasks` 逐框比对，
  **全程不改 `src/`**。定位到判据、确认影响范围后再决定要不要落地。

**反馈模板**：dev server 保持运行、停在出问题的那一页，然后说一句
「我停在当前字帖页，看一下切分」+ 期望（例如「第 3 列应是 5 个字，现在切了 8 框」）
即可，无需任何附件。读 `$DEBUG_DIR/current.json` 就知道是哪张图、页面显示哪些框，
再跑诊断脚本定位到具体判据。

**边界与坑**
- 采集脚本**绝不能抢先创建 IndexedDB**：旧版直接 `indexedDB.open('calligraphyImages', 5)`，
  在全新浏览器上下文（预览面板换了存储上下文 / 站点数据被清）会触发 0→5 升级却没有
  `onupgradeneeded`，生成 version=5、零 object store 的空库；App 随后的 `open(name, 5)`
  因版本相同不再升级，`upgradeStores()` 永远不跑，表现为「字帖库全空 + 导入失败，请重试」。
  现改为先用 `indexedDB.databases()` 确认库已存在，再**不带版本号**打开；库不存在就完全不碰。
  若本机曾被旧版污染，在**同一标签页**打开 `http://localhost:5173/__debug/reset`
  会自动删掉空库并返回首页重建（该页不加载 App、不注入采集脚本；生产包不含此路由）
- 插件是 `apply: 'serve'`，生产构建与 iOS / Android 包完全不含这段代码；
  `CALLIGRAPHY_DEBUG_BRIDGE=0 npm run dev` 可关闭。数据只在 localhost 流动、
  只写本机临时目录，不联网；`current.<ext>` 换页即覆盖，要留档先自行复制。
- 改完 `segment.js` 后 Vite 可能只热更组件、不整页 reload：浏览器仍持有旧的
  `segmentCharacters`，却用新 `segmentCache.js` 把旧框打上新算法版本写回缓存，
  `canReuseSegmentation` 会误判有效、光刷新也不重算。若发现「版本号已更新但框数没变」，
  **硬刷新 Cmd+Shift+R → 打开字帖 → 切分面板点「重新切分」** 强制覆盖缓存
  （正式发版整包代码同时更新，旧版本缓存自动过期，不会有此问题）。

### 真实图 golden 夹具

`src/utils/segment.js` 导出的 `segmentFromMasks(ink, faint, options)` 是纯计算入口，
`segmentCharacters` 只负责图像解码与参数透传，两者共用同一条切分链路。
`scripts/fixtures/segment/` 存放 14 套真实字帖的位压缩墨迹/格线掩码与逐框快照
（共 22 个 case，含无格自由切分与格线模式），测试直接调用 `segmentFromMasks` 比对。

覆盖场景包括：「石」字部件合并、两个独立「一」、方格字帖、真实拍照、密集格线、
整张界面截图、红底双联（`couplet-vertical`，两列中心距 0.483W，曾因字距
搜索上限 0.4W 被误拆成 6 列）、4 列无格行书（`cursive-vertical`，各列字数
5/4/4/4、字位与字高都不对齐，用来守住「不做跨列对齐 / 等距推断」的边界），
以及五张黑底碑帖大字拓片（`big-glyph-vertical`，「我則」曾被笔画级字距拆成
10 列 / 132 框；`big-glyph-edge-band`，右侧 8px 拓片纸边被当成第二列、
拆成 11 列 / 124 框；`big-glyph-narrow-gap`，「作我」被 8px 投影低谷劈成
2 列 / 7 框；`big-glyph-width-cap`，「凡厥」的两个正确框因宽度 473px 超过
0.85W(467.5) 被异常块过滤删光、返回 0 框；`big-glyph-stroke-pitch` 是首个多列版式，
「翁同龢書」4 字加左侧两枚印章曾被 pitch=42 拆成 6 列 / 53 框，现为 2 列 6 框；
五者都用 `free` 与 `grid` 两个 case 守住有格开关不改变结果），
以及浅褐色 4 列行草条幅 `cursive-tall-glyph`（v9 修复目标图：5 组单字曾被机械等分
水平切开，60 → 56 框；`free` 与 `grid` 两个 case 守住有格开关不改变结果，
格线检测为 none），
以及白底黑字装裱对联 `mounted-couplet`（v11 修复目标图：深色装裱边 + 黑底使暗色占比
66% 骗过反色判据，旧切 16 框穿字；`detectContentBorder` 零化边框后切 23 框，
右联 12 字逐字成框、左联「觀其」合并为一框；`free` 与 `grid` 两个 case 守住有格开关不改变结果）。
放宽判据另用 25 张 `docs/screens/` 截图做过新旧全链路逐框对比，确认除该对联外零变化。
`yi-grid / grid` 仍记录水平格线漏检一半的已知缺陷现状，将来修好时会触发差异，
需有意更新快照。`couplet-vertical / free` 的左联等分错位已由 **v12** 修复
（15 → 14 框，左联 8 → 7 框、切点落在真实字间空白），落地时同步更新了这一套快照，
其余 21 个 case 逐框零变化。
v9 落地时另更新了两套：`cursive-vertical / free` 有一个框边界吸附到真实空白
（该夹具备注本就写明算法改动需 `--update`），`full-screenshot / free` 的退化检测
由 171 框变 165 框；其余 11 套逐框零变化。

改动任何切分参数后测试会精确报出「哪张图、第几框、期望值与实际值」；
若确有意为之，用 `node scripts/test-segment-fixtures.mjs --update` 更新快照。

## 已知限制

- **微信抓取有频率限制**：短时间多次请求会被限流，需等待 1~2 分钟
- **密集粘连字帖切分不准**：字与字连笔时投影法无法可靠分开（如行草），需在编辑态用
  「本列切线 / 候选线」逐字修正；无格字帖的字位错落不做自动推断。
  高字带被机械等分切开的问题已由 v9 的空白引导切分（≤3 等分）与 v12 的超长带
  按本列字距重切（≥4 等分）修正，但 `cursive-tall-glyph` 仍留有污渍框、扁框与
  印章框，需要编辑态手动删改
- **iOS 超大图仍可能触发内存终止**：已把常驻基线从「最多 20 张完整 base64」改成
  「只读字帖元数据 + 最多 1 份当前页原图」，并做到临时 `Image` / canvas 用完即释放、
  候选线复用切分掩码、缩略图落盘且按需读取、关闭字帖清空全部内存引用。
  但 4000px 级超大图在「打开页 + 切分面板」时仍会同时存在两份解码位图，
  建议少量导入并用 Instruments 复测真机峰值
- **指针捕获与触屏手柄命中区尚未做真机点按验证**：需在 `npm run ios:copy` 后实测
  拖动、八向手柄与本列切线
- **「用其他应用打开」列表可能不含本应用**：微信的筛选规则不透明，建议用「复制链接 → 粘贴导入」
- **iOS 剪贴板授权弹窗**：每次读取剪贴板 iOS 都会弹「允许粘贴」，可在
  设置 → 应用 → 从其他 App 粘贴 → 改为「允许」后不再提示
- **大字拓片在横排模式下会返回「切分失败」**：字本就是上下排列，横排投影切不出框
  （修复前前两张会退化成 164 / 179 个笔画级小格，第三张是 10 个 grid 小格，
  第四张是 `failed / empty`，第五张是 84 个 grid 小格）。五张图现在都返回 0 框，
  请用默认竖排，或在编辑态手动加框
- **黑底大字拓片的探出笔画已基本收进框**（v10 修复）：水平扩展改用「到相邻列带
  边界的距离」左右独立限额后，`big-glyph-vertical`/`narrow-gap`/`width-cap`/
  `stroke-pitch` 的框外墨迹清零，「龢」长捺、「厥」撇尖捺脚、「作」长撇都完整入框。
  `big-glyph-edge-band` 剩约 4% 框外墨迹是拓片纸边（x=0 一列）而非笔画，属预期。
  代价是字框宽度不再整齐划一、相邻框可在列间空隙处重叠（书法字本就有大小差异）
- **印章会被当成单字输出**：`big-glyph-stroke-pitch` 左侧两枚方形印章各占一个框，
  连同正文 4 字共切出 6 框。印章在墨迹投影上与字块难以区分，自动剔除需要额外的
  印章识别（可能误删真实的小字边款），目前可在编辑态手动删框
- **装裱字帖零化边框后仍有轻微残余**：`mounted-couplet` 经 v11 边框零化从 16 错框改善到
  23 框，但零化保留全图坐标，空边距会略微改变列投影的分位阈值，使左联「觀其」两字合并为
  一框（物理裁切可分开，但需给核心函数加坐标偏移、风险更高，故取低风险的零化方案）；
  小字题款与印章仍未识别。合并框可在编辑态拆分
