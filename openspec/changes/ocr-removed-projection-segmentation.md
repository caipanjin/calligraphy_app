# 移除 OCR，改用投影切分自动切字 - 变更记录

## 变更信息

- **变更名称**: ocr-removed-projection-segmentation
- **变更类型**: 功能替换（删除 + 新增）
- **完成时间**: 2026-11-01
- **决策依据**: `openspec/changes/ocr-accuracy-tuning.md` 的实测数据

## 为什么删掉 OCR

真机验证结论：通用 OCR 引擎识别毛笔字不可用。

| 引擎 | 印刷体 | 毛笔字 |
|---|---|---|
| Tesseract（chi_sim，psm6） | ✅ | 5/8（62%） |
| PaddleOCR（PP-OCRv2） | ✅ | **0/8** |

两者都是印刷体/场景文字模型，毛笔笔画属于分布外输入。参数调优的天花板已经探到，
继续投入没有意义，因此按用户决定**整体移除识别功能**。

## 新增：投影切分自动切字

### 原理

不回答「字是什么」，只回答「字在哪」——后者是纯几何问题，毛笔字同样成立。

```
灰度 → Otsu 二值化 → 墨迹掩码
  ↓
垂直投影找列间空白 → 列
  ↓
每列内水平投影找字间空白 → 单字框
```

竖排按「列 → 行」切，横排按「行 → 列」切；读序竖排从右往左、横排从左往右。

### 关键参数（`src/utils/segment.js`）

| 参数 | 值 | 作用 |
|---|---|---|
| `INK_RATIO` | 0.004 | 投影占比低于此值视为空白 |
| `GAP_RATIO` | 0.008 | 空白带宽低于此值视为字内笔画间隙，合并 |
| `MIN_SIZE_RATIO` | 0.015 | 过滤噪点 |
| `MERGE_FACTOR` | 1.85 | 超过中位尺寸 1.85 倍视为多字粘连，等分 |

### 版面判定

1. 只有一列 → 竖排；只有一行 → 横排
2. 行数 ≤ 2 且列数 ≥ 3 → 横排
3. 其余默认竖排（书法常态）
4. 面板提供「自动 / 竖排 / 横排」手动切换

### 交互

临摹页底部「自动切字，逐字临摹」→ 抽屉内整幅图叠加切分框 → 点任意框直接进入单字临摹。

## 真实照片验证（重要修正）

首版算法用**绝对像素阈值**判定"有墨"，在实拍照片上直接失效——只切出 3 块。
原因：照片有噪点与底色不均，空白列的投影值（9~25 像素）仍高于阈值（4 像素），
于是整页被当成一整块。

### 修正

| 改动 | 说明 |
|---|---|
| 相对阈值 | 阈值 = 该轴投影 **90 分位值 × 0.15**，而非固定像素数 |
| 投影平滑 | 3 点滑动平均，抑制单像素噪声 |
| 分位数而非最大值 | 避免个别超密列把阈值抬高 |

### 验证结果（1440×2031 实拍字帖）

| 指标 | 结果 |
|---|---|
| 切分结果 | **4 列 × 5 字 = 20 框**（竖排） |
| 每框墨迹覆盖率 | 24% ~ 36%（中位 29%），**无空框** |
| 同列相邻框间空隙墨迹 | ≤ 8%（说明切在真实空白处） |
| 耗时 | < 40ms |

### 回归测试

新增 `scripts/test-segment.mjs`（`npm test`，6 项）覆盖：
字符带识别、字内间隙合并、噪点过滤、尾部收尾、相对阈值、Otsu 阈值。

## 修复：切分后「下一字」位置偏移

**现象**：从自动切字选中第 1 个字后点「下一字」，跳到的位置不是切分出的第 2 个字。

**原因**：切分结果是**不规则网格**（每列宽度 15.2%~17.6%、每字高度 10.5%~13.9% 各不相同），
而导航用的是 `charNav.js` 里的**等距步进**——每次固定移动一个 `viewBox.height`。
从切分框出发，第一步就累积误差，越点越偏。

**修复**：让导航跟着切分网格走。

- `SegmentSheet` 选中时把 `{ boxes, index }` 一并挂到 `selectedCharacter.grid`
- `PracticeView` 的「上一字 / 下一字」优先按 `grid.boxes[index ± 1]` 取**真实字框**
- 字符滑轨同样改用网格里前后各 2 个真实框（每格按自己的宽高渲染）
- 无网格（手动点选）时仍走原等距推算，行为不变

**验证**（实拍 20 字字帖，逐字比对 viewBox 中心与切分框中心）：

| 场景 | 结果 |
|---|---|
| 正向连点 6 次「下一字」 | 6/6 中心偏移 **dx=0, dy=0**（含跨列：x 从 1144 → 841） |
| 反向连点 5 次「上一字」 | 5/5 精确 |
| 滑轨跳转（+2 个字） | 精确 |
| 手动点选后「下一字」 | 下移 360px = 字高，尺寸不变 |

## 第二轮修正：密集字帖改用「字距拟合网格」

**现象**：第二张实拍图（4283×4530 的密集字帖）只切出 8 块，每块高 3417px——等于整列，
说明列切出来了但**列内的字没切开**。

**原因**：这张图字距极密，投影低谷很浅（字与字之间只差几个像素的墨迹），
相对阈值 0.15 仍然切不开，整列被当成一个字；而 `splitOversized` 以"中位字高"为基准，
当所有块都同样过高时基准本身失效。

**修正：投影 + 网格的混合策略**

1. 用**列投影自相关**估字距（搜索范围限制在图宽 8%~40%，避免锁到笔画级周期）
2. 仍先走投影切分
3. 若切出的字块明显大于字距（> 1.8 倍）→ 判定投影失效，改用**规则网格拟合**：
   按字距把墨迹外接框均分为 N 列 × M 行，逐格检查墨迹覆盖，丢弃空格
4. 网格模式下版面回落为竖排（投影判定此时已失效）

**验证**

| 图片 | 策略 | 结果 |
|---|---|---|
| 图1（1440×2031，4 列 5 字） | 投影 | 20 框，尺寸 218~260 × 198~282（跟随真实字框） |
| 图2（4283×4530，密集字帖） | 网格 | **36 框（6×6）**，覆盖 4.4%~39.0%，**0 空格** |

两张图的「下一字」导航均 5/5 精确。

**新增测试**（`npm test` 共 10 项）：字距估计（周期 20 / 50）、网格拟合（3×2 竖排顺序、空格过滤）。

## 第三轮修正：字不在正中（网格方案废弃）

**现象**：密集字帖切完进入单字临摹，字不在画布正中。

**根因（两个叠加）**：

1. **单位重复换算**：`toSource()` 已把坐标转到原图尺度，退化检测里又除以一次 `scale`，
   导致字框被放大 2.8 倍，"是否退化"永远为真 → 总是走网格兜底
2. **网格方案本身不适用**：这张图每列字数不同（有的 5 个、有的 6 个），
   统一网格的格子会跨到相邻字上；且版面判定规则把竖排字帖误判成横排，
   导致列内的字距拆分根本没执行

**修正**：

- 修掉重复换算
- 版面判定改为「只有一行→横排，其余默认竖排」（规则网格下两种解读切出的框相同，只差阅读顺序）
- **废弃网格兜底**，改为「投影为主 + 按字距拆分粘连」：
  先用投影找列/字带，宽度超过 1.6 倍字距的带按字距等分（解决列粘连与字粘连）
- 过滤明显小于中位字块的碎片（贴边截断的半行）

**效果对比（密集字帖）**：

| 指标 | 修正前（网格） | 修正后（投影） |
|---|---|---|
| 切分策略 | 网格 36 格（等大 692×707） | 投影 31 框（552~648 × 300~694） |
| 重心水平偏移 | 2.4% | 2.9% |
| 重心垂直偏移 | **8.5%（最大 42%）** | **3.3%（最大 12%）** |
| 框尺寸 | 全部相同（会跨字） | 跟随真实字 |

另一张图（4 列 5 字）无回归：20 框，偏移 1.6% / 3.0%。

## 第四轮：列内字数归一 + 切分结果持久化

### 列内字数归一（30 字真值对齐）

实测该字帖每列字数应为 6 × 5 = 30，此前切出 31 个——多出的一个是底部贴边的非文字块。

修正：**列内字数取众数**。字帖每列字数通常一致（末列可能少），把多于众数的列从末尾裁掉。
实测各列 5/5/6/5/5/5 → 众数 5 → 切出 **30 个**，与真值一致。
另一张图（4 列 5 字）保持 20 个，无回归。

### 切分结果持久化

| 项 | 说明 |
|---|---|
| 存储 | IndexedDB 新增 `segmentations` store（DB 版本 1 → 2，`onupgradeneeded` 自动建表） |
| 键 | `图片内容哈希:版面模式`（竖排/横排各自一份） |
| 内容 | 字框数组、版面、策略、原图尺寸、时间戳 |
| 失效 | 删除字帖 / 清空字帖时连带清理；改了版面模式则各算各的 |
| 重算 | 面板「重新切分」按钮强制绕过缓存 |

**验证**：读缓存 **3ms** vs 实时计算 **209ms**（快约 70 倍），两次结果均为 30 框。
新增 4 项哈希单测（一致性、区分度、长度差异、8MB 输入耗时 < 500ms），`npm test` 共 **14 项**。

## 第五轮：竖排优先 + 按列宽判定字块

**前提修正**：字帖几乎都是竖排，此前「横排优先」的版面判定方向错了。

### 改动

1. **版面判定改为竖排优先**：只有「多列但仅一行」这种明确横幅形态才判横排，其余一律竖排
2. **竖排的几何先验**：一个字的高度应接近列宽（实测比值 0.7~1.1）
3. **`splitTallGlyphs`**：块高超过列宽 1.25 倍 → 判定上下两字粘连，按列宽等分
4. **修正跨轴误用**：竖排列内是按「高度」切字，不能拿横向字距（pitch）去等分
5. `mergeSplitGlyphs` 增加尺寸约束：只有「一块明显小于正常字」时才可能是一字被切开，
   避免把上下相邻的正常字误并

### 第三张图（1080×880，4 列竖排）实测

| 物理列 | 高/宽比 | 处理结果 |
|---|---|---|
| 列4（最右） | 0.69 / 0.91 / 0.94 / 0.75 / 1.01 | 5 字（正常） |
| 列3 | 1.09 / 0.86 / 1.04 / 0.98 | 4 字（正常） |
| 列2 | 1.07 / 0.69 / 1.07 / 1.10 | 4 字（正常） |
| 列1（最左） | 1.11 / 0.80 / 0.96 / **1.44** | 末块偏高 → 拆为 2，共 5 字 |

合计 **18 字**。其中列1 末块（高 234 / 列宽 162）是否为两字粘连，**待用户确认**。

新增 4 项竖排规则测试（过高拆分、正常不拆、部件合并、正常字不合并），`npm test` 共 **18 项**。

## 第六轮：格线检测（手动开关）

### 背景：之前误判「无格」

图1（1440×2031）实际带格线，我最初判成无格。原因：**格线是 RGB(176,170,134) 的浅褐细线**，
比纸面 (220,211,182) 略暗、比笔画（近黑）浅得多，Otsu 二值化直接把它归入背景。

### 为什么不做「自动判断有无格」

试了 5 种判据，全部无法可靠区分真格线与笔画伪周期：

| 判据 | 结果 |
|---|---|
| 贯穿度 | 图1 格线仅覆盖 15%（被墨迹打断） |
| 等差序列 | 图2 的笔画周期 675 同样高度等距 |
| 线宽 | 两者均为 3~7px |
| 中间调占比 | 图2 伪周期反而更高 |
| 直线笔直度 | 图2 某位置暗度 50.9，强于图1 真格线 0.1~3.7 |

且**用周期拟合网格的效果不如投影切分**（图1：25 格 vs 20 格；图2：42 格 vs 30 格）。

**因此改为手动开关**：面板上加「这张字帖带格子线」，勾选后按格线切分。

### 实现

1. `buildInkMask` 新增 `faint` 掩码：比 7×7 邻域中位背景暗 6 灰阶以上的非墨迹像素
2. `detectGridLines`：对 faint 做投影找强峰 → 提取最长等差序列（格距需高度一致）
3. `boxesFromGridLines`：相邻格线之间的区域即为单元格，按竖排/横排排序
4. `segmentCharacters({ hasGrid })`：开启时走 `grid-lines` 策略，直接返回单元格
5. 缓存键加入 `grid/free`，两种模式各存一份

### 实测（图1，1440×2031）

| 模式 | 结果 |
|---|---|
| 投影（默认） | 20 框，strategy=projection |
| **按格线** | **20 框，strategy=grid-lines，kind=full**，格距 270×282，4 列 |

两种模式结果一致，说明格线检测准确。

新增 4 项格线单测（全格识别、无格返回 none、竖排/横排排序），`npm test` 共 **22 项**。

## 第七轮：手动编辑切分框 + 阈值修正

### 阈值 1.25 → 1.7

用户确认 IMG_4575 最左列末字（高 234 / 列宽 162 = **1.44 倍**）是**一个字**，之前被误拆。

实测三张图的高宽比分布：

| 情况 | 范围 |
|---|---|
| 正常字（图3） | 0.69 ~ **1.44** |
| 粘连块（图2） | **1.99** ~ 3.24 |

两者之间有清晰间隙，阈值取 **1.7**（两侧各留约 18% 余量）。

同时修正：`normalizeColumnCounts` 原先按众数无差别削平各列，会误删正常的多字列
（图3 物理第4列确实有 5 个字）。改为**只丢弃贴边或极小的残块**，正常多字列保留原样。

### 手动编辑切分框

自动切分不可能 100% 准确，因此提供手动修正：

| 操作 | 说明 |
|---|---|
| 编辑开关 | 面板右上角铅笔图标，进入/退出编辑模式 |
| 选中 | 点击任意框高亮选中 |
| 删除 | 移除误切出的框（如底部的非文字块） |
| 合并 | 与该框最邻近的框合并成一个外接框（修复被切开的字） |
| 拆分 | 把选中的框对半拆开（竖排按高度、横排按宽度） |
| 还原 | 放弃所有手动修改，回到自动切分结果 |

实现：`src/utils/boxEdit.js`（纯函数），编辑结果只存在内存中，不写回缓存，
避免污染自动结果。

### 验证

- 三张图：图1 = 20 ✓、图3 = **17** ✓、图2 = 31（真实 30，多 1 个残块，可用编辑删除）
- 编辑功能端到端：删除 31→30 ✓、合并 30→29 ✓、拆分 29→30 ✓、还原 →31 ✓
- 退出编辑后点框正常进入临摹 ✓
- `npm test` 共 **31 项**（切分 23 + 编辑 8）

## 第八轮：完整持久化（切分结果 + 手动调整 + 字帖设置）

### 三个层次都持久化

| 内容 | 存储 | 键 |
|---|---|---|
| 自动切分结果 | `segmentations` | `图片哈希:版面:grid/free` |
| 手动调整结果 | `segmentations` | 同上 `+:manual`（与自动结果分开，互不覆盖） |
| 字帖设置（版面模式 / 是否带格线） | `segmentationSettings`（新增，DB v3） | `图片哈希` |

关键设计：**自动结果与手动结果用两个键**。早先共用一个键导致「还原」写回的是被覆盖后的数据，
无法回到自动切分结果；拆成两个键后「还原」只需删除 `:manual`，自动结果原样保留。

### 打开即见切分结果

进入临摹页时自动读取已保存的切分，把字框**直接叠在图片上**（`.stage-grid`），
点任意框即进入单字临摹，不必再点「自动切字」。

读取顺序：手动结果 → 自动结果 → 无（此时退回手动点选）。

### 字帖设置记住

`SegmentSheet` 打开时先读 `segmentationSettings` 恢复上次的「版面模式」和「带格子线」，
恢复完成后才触发切分（避免用默认值先切一次再重切）。用户改动即时写回。

| DB 升级 | v3，新增 `segmentationSettings` 表，读写往返正常 |
| 首次打开 | 无网格（无缓存） |
| 勾选带格线 → 关闭 | 舞台**直接显示 20 个网格** |

## 第九轮：无缓存时按已存设置自动切分

**问题**：用户勾选了「带格子线」并切分过一次，但重新打开字帖时并没有按格子方式切分——
必须先手动点「自动切字」才会生效。

**原因**：临摹页加载网格时只做「查缓存」，查不到就什么都不显示，**不会按已保存的设置主动切分一次**。

**修正**：加载顺序改为

1. 查手动结果 → 查自动结果（命中即用）
2. 都没有 → 读该字帖的 `segmentationSettings`（版面模式 / 是否带格线）→ **按此设置自动切分一次**
3. 切分成功则写回缓存，下次直接读取

切分失败的异常被静默捕获，退回手动点选，不影响打开字帖。

### 验证

| 场景 | 结果 |
|---|---|
| 全新状态（无设置无缓存） | 进入即显示 20 个网格，缓存同步写回 |

## 第十一轮：修复阅读顺序与返回后网格消失，并取消横排

### 1. 「下一字」方向错误

**现象**：单字临摹里「下一字」变成横向（从右往左逐字走），应沿同一列自上而下。

**根因（三处叠加）**：

| 位置 | 问题 |
|---|---|
| `sortByReadingOrder` | 先按 y 分组再按 x 排 → 等于逐行横向走 |
| 竖排外层循环 | `[...colBands].reverse()` 写死了从右往左，与内层排序冲突 |
| `normalizeColumnCounts` | 内部按分组重建数组，把排好的顺序又打乱 |

**修正**：

- 新增统一排序：竖排 = 先按列（`b.x - a.x`，右侧在前），同列内 `a.y - b.y`
- 竖排外层不再 reverse，遍历顺序无关紧要，最终顺序统一由排序函数决定
- 归一化之后再排一次

**验证**（图1）：第 1-5 字 x≈1002、y 从 120 → 1229 递增（同列向下），第 6 字才换到左列。

### 2. 返回后网格消失、字点不动

**根因**：网格渲染时读取 `frameRef.current` 取图片尺寸。返回时组件重新挂载，ref 为 `null`，
所有框 `return null`，网格整体消失。

**修正**：改用 `naturalSize` state（进入时用 `new Image()` 探测原始尺寸），不再依赖 ref。

**验证**：返回后网格仍为 20 个，可继续点框进入临摹。

### 3. 取消横排

字帖一律按竖排处理（中文书法常态）：

- 移除「自动 / 竖排 / 横排」切换，固定竖排
- 删除横排分支、`splitOversized`（已无调用者）
- 格线检测中的「横线」保留（横线是格子的一部分）

## 第十七轮：重新切分未保存 + 按钮被长字帖遮挡

### 1. 「重新切分」的结果其实没保存

**现象**：点「重新切分」后界面变回自动结果，但关闭重开又回到旧的手动调整结果。

**根因**：手动调整存在 `:manual` 键，读取时**优先于**自动结果。

## 第十八轮：保存单字的取景调整（放大/缩小/移动）

## 第十九轮：公众号导入的三个问题修复

### 1. 重复图片

**现象**：同一张图在列表里出现两次。

**根因**：公众号会把同一张图存成**不同的 CDN 路径**（`sz_mmbiz_jpg/...` 与
`mmbiz_jpg/...`），URL 完全不同但内容字节一致（实测 md5 相同）。

**修正**：URL 层面去重不够，改为**下载后按内容哈希去重**（`ImportSheet.quickHash`）。

### 2. 导入后图片无法加载

**现象**：选择图片并导入后，字帖显示不出来。

**根因**：`CapacitorHttp` 在 `responseType: 'arraybuffer'` 下返回的是 **base64 字符串**
（不是 ArrayBuffer），原代码按 ArrayBuffer 二次编码，产生双重 base64 → WebView 无法解码。

**修正**：
- 判类型处理（字符串直接用，ArrayBuffer 才转 base64）
- MIME 改用**文件头魔数嗅探**（`iVBORw0KGgo`=PNG、`/9j/`=JPEG 等），不再依赖 URL 参数
- 兼容 `wx_fmt=jpg`（不是 jpeg）

### 3. 过滤干扰图片

**规则**（`looksLikeSticker`）：宽高都 ≥300px、宽高比 0.33~3、
正方形且 <1000px 视为头像/二维码/表格截图。

实测效果（《在董其昌的笔下，看李白的月亮》）：

| 阶段 | 数量 |
|---|---|
| 文章提取 | 14 张 |
| 尺寸/比例过滤 | 保留 10 张（滤掉 272x272 图标、390x390 表格、390x220 横幅、895x895 正方形）|
| 内容哈希去重 | **9 张** |

### 附带发现：微信抓取的风控规律

反复测试确认了两条硬规律：

1. **请求头越少越稳**：仅发 UA → 200 且含正文；
   加 `Accept`/`Accept-Language` → 302 跳验证码页
2. **有按 IP 的限流**：短时间多次抓取会返回 31652 字节「精简页」
   （HTTP 200 但无 `js_content`），冷却数分钟后恢复

应对：
- vite 开发代理改为**自定义中间件**（node 原生 https，只发 UA，不透传浏览器 Cookie/Referer）
- 前端检测「精简页」特征并给出准确提示，不再是误导性的「没有找到图片」
- 抓取结果缓存 10 分钟，避免重复请求

## 第二十轮：视觉去重（同一幅字帖的多个导出）

### 问题

文章 `HdX6lU0V4xopJd9F_D53xw` 实际只有 **1 张**字帖，但导入列表出现多张。

### 根因

公众号会把**同一幅字帖导出成多个尺寸**：

| 版本 | 尺寸 | 说明 |
|---|---|---|
| 原图 | 2539x3279 | 正文原图 |
| 压缩版 | 2539x3279 | 尺寸相同但字节不同（md5 不同）|
| 缩略 | 1280x1706 | 缩小 |
| 裁切 | 1280x1280 | 裁成正方形 |
| 缩略 | 1280x1653 | 缩小略裁 |

**字节哈希去重完全失效**（md5 都不同），必须用**视觉相似度**。

### 方案：16x16 灰度指纹

不用 canvas 缩放（`drawImage` 的插值是平台相关的，同一张图不同尺寸缩放后
哈希差异能到 23）。改为**分块平均**：把图切成 16x16 网格，每格取平均亮度，
得到 256 维指纹，用归一化 RMS 距离比较。

实测距离（同一篇文章）：

| 对比 | 距离 |
|---|---|
| 同一幅字的 5 个导出 | 0~7 |
| 封面横幅 vs 字帖 | 11 |
| 二维码 vs 字帖 | 39~40 |

阈值取 **10**。

### 效果

```
URL 提取 7 张
→ 尺寸过滤 2 张（1280x719 横幅、272x272 图标）
→ 视觉去重 4 张（同一幅字的各尺寸）
= 保留 1 张（2539x3279 原图）
```

同时加了「保留最高分辨率」逻辑：遇到重复时保留像素更多的版本。

### 附带收紧：横版比例上限 3 → 1.5

字帖基本是竖版或接近方形；比例 >1.5 的多是封面横幅（实测 1280x719 比例 1.78）。

## 第二十二轮：过滤时机提前（选择列表不再显示重复图）

### 问题

去重和过滤虽然生效，但**只在点「导入」时才执行**。用户在图片选择界面
看到的仍是未过滤的原始张数（例如 5 张），选完点导入才发现只导入 1 张。

### 根因

`handleFetch` 里 `setImages(urls)` 直接把所有 URL 塞进列表，
过滤逻辑写在 `handleImport` 里。

### 修正

把「下载 + 尺寸过滤 + 视觉去重」抽成 `prepareImages()`，
在**抓取完成后立即执行**，把最终可用列表作为选择界面数据源。

- 抓取后显示进度「正在分析 N/M…」
- 完成后标题显示「N 张 · 已选 N」
- 有跳过时在网格上方显示说明：「已自动跳过 X 张重复或无关的图片（原图 Y 张）」
- `handleImport` 直接使用已下载好的图片，不再重复下载

### 界面细节同步修正

- 标题过长被挤成两行 → 精简为「N 张 · 已选 N」，跳过数移到独立提示行
- 「全不选」按钮文字换行 → 改为「取消全选」，并给 `.sheet__footer .btn` 加 `white-space: nowrap`

## 第二十三轮：改用「正文图片提取」替代尺寸/视觉猜测

### 问题

之前靠「尺寸规则 + 视觉相似度」去猜哪些是字帖图，实测仍会漏过滤
（重复图、封面、二维码混进列表）。

### 根本原因

**猜不如认**。微信页面里这些干扰图都有明确标记：

| 干扰类型 | 页面中的标记 |
|---|---|
| 作者头像 | `class="jump_author_avatar"` |
| 跳转二维码 | `class="jump_wx_qrcode_img js_qrcode_img"` |
| 小程序码 | `class="js_pc_weapp_code_img"` |
| 公众号头像 | `var round_head_img` |
| 分享封面 | `property="og:image"` / `twitter:image` |
| 封面变量 | `var msg_cdn_url` / `d.cover` / `cdn_url_1_1` / `cdn_url_235_1` |

### 修正：extractContentImageUrls

1. 逐张图判断（不是按大片段切分 —— 微信一个 div 里可能同时有封面和正文图，
   整段丢弃会误杀正文图，实测 h1 有 8 张图挤在同一片段）
2. 只看**紧邻上下文**（从该 URL 往前到最近一个 `<img` / `<meta` 标签），
   窗口不能大，否则会把上一张图的干扰标记算进来（实测会误杀）
3. 有干扰标记 → 跳过；否则保留

### 效果对比

| 文章 | 全篇正则 | 正文提取 | 最终（含尺寸过滤）|
|---|---|---|---|
| 董其昌（h1） | 7 张 | 2 张 | **1 张**（1280x719 封面被尺寸过滤）|
| 翁同龢之父（h2） | 5 张 | 1 张 | **1 张**（976x2398）|

两篇都精确得到 1 张，与「实际只有一张图片」一致。

### 保留的兜底

尺寸规则与视觉去重**仍保留**作为二次保险：
- 正文提取负责排除「结构上的干扰图」
- 尺寸规则排除「过小/比例异常」的图
- 视觉去重处理「同一幅字的多个尺寸/裁切」

npm test 共 74 项（新增正文提取 5 项）

## 第二十四轮：修复长图在临摹页被上下裁切

### 现象

导入文章 `bPLmHqqI7iiCI-_9O8QbAA` 的图片（1080x1440，比例 0.75）后，
临摹页显示时**上下被裁掉一部分**。

### 根因

`stage-frame` 的 `overflow: hidden` + 图片只设 `width: 100%; height: auto`：

- 图片按宽度撑开 → 高度按比例算得 1440/1080 × 容器宽
- 该高度**超出容器可用高度** → 被 `overflow: hidden` 裁掉
- 容器 `align-items: center` → 上下各裁一半

### 修正

1. **容器宽高比绑定图片真实比例**：给 `.stage-frame` 设
   `aspectRatio: naturalWidth / naturalHeight`，容器与图片完全重合
2. 图片改为 `width: 100%; height: 100%; object-fit: contain` 填满容器
3. 移除 `Magnifier` 的内联 `style={{ width: '100%', height: 'auto' }}`，
   改用 `className="stage-image"` 由 CSS 控制

这样切分框的百分比定位也与图片坐标系一致（此前容器比图片高，红框会错位）。

### 顺带修复

- 顶部大片空白：`.practice__body` 的 `justify-content` 由 `center` 改为 `flex-start`
- 提示气泡长期压住字帖底部：加 `hint-out` 动画，4.5 秒后淡出

### 验证（1080x1440 测试图）

```
自然比例 0.750 → 显示比例 0.750   ✓ 不变形
imgFullyVisible: true              ✓ 完整显示
hintVisible: false                 ✓ 提示已淡出
红框与文字精确对齐
```

## 第二十五轮：修正误杀正文图（提取到裁切版而非完整版）

### 现象

文章 `bPLmHqqI7iiCI-_9O8QbAA` 导入后图片**上下被裁**。
用户提供了正常参考图（1080x2009），对比发现我们提取到的是 **1080x1440 的裁切版**。

### 根因

这篇文章的正文图不在 DOM 里，而是在 **JS 数据结构**中：

```js
picture_page_info_list: [ { cdn_url: '...1080x2009...' } ]   // 正文图（完整）
watermark_info:         { cdn_url: '...1080x2009...' }       // 带水印版
share_cover:            { width:'1080', height:'1440', cdn_url: '...' }  // 裁切封面
cdn_url_1_1:            '...1080x1080...'                     // 方形封面
```

我此前把通用的 `cdn_url` 字段当成了干扰标记，结果**把正文图全部误杀**，
只剩 DOM 里的裁切封面。

### 修正

- 移除 `'cdn_url:'` 这个通用标记
- 改为精确排除 `share_cover`、`watermark_info`、`cdn_url_1_1`、`cdn_url_235_1`、`thumb_url`

### 效果

正文提取 3 张（1080x1440、**1080x2009**、1080x1440），
视觉去重时保留像素最多的 → **1080x2009 完整版**。
