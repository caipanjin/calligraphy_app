# OCR 识别效果调优 - 变更记录

## 变更信息

- **变更名称**: ocr-accuracy-tuning
- **变更类型**: 缺陷修复 / 效果调优
- **完成时间**: 2026-11-01
- **触发问题**: 真机反馈「毛笔字几乎不能识别，出来的都是英文」

## 结论先说

**tesseract 不是毛笔字的合适引擎。** 实测调优把命中率从 50% 提到 60%，去掉了英文乱码，
但天花板就在这里——它是印刷体模型，毛笔笔画属于分布外输入。要真正解决，需要换引擎（见文末）。

## 实测数据

测试集：用开源毛笔字体（马善政毛笔楷书，MaShanZheng）渲染的竖排字帖，
白底黑字、无透视无噪点——**比真实手机拍摄的照片容易得多**，因此真实场景只会更差。

### 实验一：单字识别（10 个字，PSM / 语言 / 预处理对照）

| 配置 | 命中率 |
|---|---|
| A 现状：`chi_sim+eng` / psm3 / gamma | 0% |
| B `chi_sim` / psm3 / gamma | 0% |
| C `chi_sim` / psm6 / gamma | 40% |
| D `chi_sim` / psm6 / otsu 二值化 | 40% |
| E `chi_sim` / psm6 / 原图 | 40% |
| F `chi_sim` / psm10(单字符) / otsu | 40% |
| G `chi_sim` / psm10 / gamma | 40% |
| H `chi_sim` / psm10 / 原图 | 40% |

→ **PSM 是决定性变量**：默认 psm3 在单字图上直接输出空；psm6/10 才出字。
→ 预处理（gamma / otsu / 原图）影响很小，tesseract 内部还有一层自适应二值化。

### 实验二：竖排整页（16 字，字符召回率）

| 配置 | 召回率 | 识别样例 |
|---|---|---|
| `chi_sim` / psm3 / gamma（原默认） | 50% | 着诚永春在和之仅九备初恬年只修哈 |
| `chi_sim` / psm6 / gamma | **56%** | 人养诚永于春在和会之奚九矫初恬年 |
| `chi_sim` / psm6 / 原图 | 50% | 会养蕊处于看在和会之有九备初丑年 |
| `chi_sim_vert` / psm3 / gamma | 0% | 产轩六产遍座仆汶广丽寺由蔬呈上号 |
| `chi_sim_vert` / psm6 / gamma | 0% | 下二加上涌遍洛哺修泌广座寺由蔬 |
| `chi_sim_vert` / psm5 / 原图 | 44% | 永大九年咸在肥线莫春之方会于会符 |
| `chi_sim+chi_sim_vert` / psm6 | 50% | 下二加于春在和会之奚九矫初恬年 |

→ **竖排模型（chi_sim_vert）反而更差**，说明瓶颈不在排版方向，而在笔画形态。

## 本次改动

1. **移除 `eng`**：`OCR_LANGS` 由 `chi_sim+eng` 改为 `chi_sim`。
   这是「输出一堆英文」的直接原因——中文识别失败时 tesseract 会拿拉丁字母去凑。
   资源脚本同步去掉 `eng.traineddata.gz`，包体减少 1.9MB（12MB → 9.9MB）。
2. **默认 PSM 改为 6**（单块文本）：整页召回率 50% → 56%，单字从 0% → 40%。
   `recognizeText` 新增 `psm` 参数，缓存键包含 psm。
3. **UI 显示置信度**：结果标题显示「N 字 · 置信度 X%」；
   低于 75% 时给出提示「毛笔字与印刷体差异较大，结果仅供参考，建议直接点选单字临摹」，
   避免用户被错误结果误导。
4. 清理未采用的实验产物（`chi_sim_vert`、standard/best 模型）。

端到端复测（真实应用，毛笔字体页面）：**60% 字符命中、置信度 63%、无英文输出**。

## 换引擎的可行性调研

| 方案 | 状态 | 说明 |
|---|---|---|
| PaddleOCR（`@paddlejs-models/ocr`） | **未能验证** | 包可安装（1.2.4，PP-OCRv2 + WebGL），但在无头 Chrome 中 `init()` 卡住（模型从百度 CDN 拉取失败），无法给出可信数字 |
| onnxruntime-web + PP-OCRv4 | 未验证 | 需自行实现检测框后处理与 CTC 解码，工作量中等 |
| 云端 OCR（百度/腾讯/阿里） | 未采用 | 准确率最高，但需联网 + API Key，破坏离线承诺 |
| 专用书法识别模型 | 未采用 | 无现成 JS 可用实现 |

**建议**：若要把识别做到可用，优先验证 PaddleOCR（真机 + 自托管模型，约 15-20MB）。
若短期不动引擎，则把 OCR 定位为「辅助」而非「主路径」——当前 UI 已按此调整。

## 遗留

- 未在真实毛笔照片上做基准（合成字体仍偏「干净」）
- PaddleOCR 未验证，需在真机 + 可用网络环境复测
